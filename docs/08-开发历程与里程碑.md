# 08 · 开发历程与里程碑

> 时间线按真实推进顺序整理，标注每个阶段的**关键判断**——比"做了什么"更有参考价值。

---

## 阶段 0 · 起点：想复刻别人的 AI 玩家（10-15）

原始设想是复刻一套已经存在的"AI 玩家"系统，让机器人在服务器里自动活动。

| 探查项 | 结论 |
|---|---|
| 对方的桥接 `127.0.0.1:8765` | 只监听回环，**只在他机器上可达** |
| 核心代码 `index.js`（~2500 行）/ `mods/` / `launcher/*.py` | **只在他机器上**，文档只有 2 篇 |
| 本地复刻能得到什么 | 一个**新账号新玩家**，空背包、从零开始 |
| 能否互相控制 | 不能。运行时永远是两台独立机器 |

**关键判断**：这条路走不通 —— 复刻 ≠ 接管。于是改为**自己造一套**：
不做客户端自动化，走协议层。

> 这一阶段唯一的产出是"排除了错误方向"，但价值很大：省下了几十 GB 的模组包与环境折腾。

---

## 阶段 1 · 协议层攻坚（10-16 ~ 10-18）

目标：不启动游戏客户端，让一个 Node 进程进 NeoForge 服务器。

| 步骤 | 结果 |
|---|---|
| 朴素离线连接 | 卡在 `configuration`，20s 不被踢也不进 PLAY |
| 回应空通道表 | **13ms 内被踢** `multiplayer.disconnect.incompatible` |
| 抓失败载荷 | 987 B，服务端**逐条列出缺失的 1305 个通道** |
| 补齐通道表 | 日志出现 `>> C->S neoforge:register（1305 通道）` + `✅ 协商成功` |
| 首次进服 | `bot_one` 进服成功，`online:true authed:true` |
| 首次死亡 | 上线 5 分钟被熊击杀（0 级木剑无甲 + 自动战斗） |

**关键判断**：通道表是硬门槛，拿不到就没有这条路。
补到之后，剩下的问题全是工程问题（补丁、认证、重连）。

同期修掉交接包的 4 个缺陷：硬编码抓包路径、`package.json` 假版本号、
`patches/` 缺第二处、注册表无空值保护。

---

## 阶段 2 · 控制台 MVP（10-18）

目标：一个网页里同时管多个 bot。

| 设计决策 | 原因 |
|---|---|
| 只暴露"统一语义"（7 个动作） | 协议 bot 十几个动作、客户端 bot 100+，不统一就得写两套 UI |
| 适配器收口 `build_action()` | 接新 bot 只加一个子类 |
| bot 间用游戏内 `@目标 动词 参数` | 两人都能在游戏里看见，可审计 |
| 目标租约 60s | 两个 bot 抢同一目标会打架 |
| 纯标准库 + 单页 HTML | 零安装、改一行刷新即生效 |

当日实测（mock 环境）：会合 3.2s / 语言指挥 3.2s / 接力 ✓ / 冲突被租约拒绝 ✓。

---

## 阶段 3 · 接真 bot 与只读闸门（10-18 ~ 10-19）

| 里程碑 | 说明 |
|---|---|
| 真 bot 接入 | 控制台 ↔ 真 `forge-live.mjs` 打通 |
| 只读模式 | `dispatch()` 入口拦截，6 个危险动作全拒、6 个查询动作全通 |
| 全服聊天聚合 | 一个在线连接即可覆盖全服公屏 |
| 反向接入 | `reporter.py` 让 NAT 后的第三方 bot 主动连 |
| 背包面板 | 拖拽装备、主手/副手、盔甲白名单 |

**为什么先做只读**：对方那只 bot 是唯一资产（高等级、死亡掉经验），
且背包解析当时不稳。只读接入能在零风险下验证对接是否成立。

## 阶段 4 · 桌面化（10-19）

| 产物 | 行为 |
|---|---|
| `gui.py` + pywebview | 开窗口 = 全起；**关窗口 = 强制全停**（含残留 `forge-live.mjs`） |
| `launcher.py` | 无窗口启动器，拉起后常驻（备用形态） |
| `build_gui.py` | PyInstaller onedir 打包，防目录嵌套 |

两个打包结论：必须 onedir（onefile 的 job 限制会让子进程 breakaway 失败）；
`_internal/` 必须跟 exe 一起移动。

---

## 阶段 5 · 去 PC 化（10-20）

目标：整套跑在安卓 Termux，PC 全程关机。

| 里程碑 | 结果 |
|---|---|
| 手机侧 4 服务起来 | 2 bot + 控制台 + 大脑，全在 `$HOME` |
| 关 PC 验证 | 02:36 停 PC 下载服务 → 02:59 bot2 拿到坐标 `253.5, 77.0, -1157.5` |
| 一键更新闭环 | PC `make_deploy.py --serve` → 手机 `update.sh` |
| 脚本体系成型 | setup / start_session / restart / stop / update / check / watchdog |

本轮修掉 5 个真 bug：`reconnects` 清零、`authed` 兜底、`wait` 改心跳、
三服务独立判断、`--ip auto` 动态探测。

## 阶段 6 · 打磨（10-21 ~ 10-24）

| 项 | 之前 | 之后 |
|---|---|---|
| 手机首屏 | 十几秒，图标逐个超时 | ~1s（负缓存 + 熔断） |
| 「服务器在线」 | 永远"读取中…" | 取第一只在线 bot，全离线时明确提示 |
| 日志 | 刷满 `BrokenPipeError` | HTTP/1.1 复用 + 吞异常 |
| 代理环境 | 请求全部 404 | 统一 `urlparse(path).path` |
| AuthMe | 握手成功却循环重连 | 登录守卫（3 次 + 双信道识别） |
| 控制台自检 | 只 `echo` 地址 | 真 `curl` 到 200 才算通 |
| 看门狗 | 无 | 8900 连续 2 次失败自动重启 |

## 如果重来一次，会怎么做

1. **第一天就写探针**，而不是反复手改主程序试错（省下的时间以小时计）；
2. **先跑通单 bot 全链路**，再上多 bot 与控制台（否则问题互相掩盖）；
3. **每个"缺文件静默降级"的依赖都加启动自检**（通道表、补丁、`scenarios.py`）；
4. **从第一版就记录"现象-根因-解法"三元组**（本仓库的 05 就是这么攒出来的）；
5. **手机端第一天就用脚本，不手敲命令**（软折行浪费的时间比写脚本多得多）。
